## 3. The diagnostics

Every message is in `include/leapc_errors.inc`, after its number, as a quoted text, for example `E_SYNTAX EQU 20 ; "SYNTAX ERROR": ...`. `tools/gen_diag.py` reads them at every build and writes `build/diag_text.inc`:

- **`DG_WORDS`:** each of the 70 distinct words is stored once, with bit 7 set on its last character.
- **`DG_MSGS`:** each message is stored as the numbers of its words (1 B each, bit 7 on the last), in key order. A key is stored only where the numbering jumps (`DG_KEY`, 9 times); otherwise a message's key is the previous one + 1. A compile error's key is its number; a runtime error's is `DG_RT` (`$80`) + its number.

`DG_APPEND` (85 B) appends `n: MESSAGE` to the report buffer. The table is 555 B; the raw texts with their numbers would take 733 B. The generator checks that every report fits its 32-column row, and the tests compare all 44 texts in the ROM against the file (`diag-table`).

**Bank rule 3.** The diagnostics run in the EXROM, called by the shell after `SH_COMPILE` (the compile's HOME trampoline) has paged the EXROM back in. They read only the compiler's error cells (`CC_ERRNUM`, `CC_ERRLINE`) and their own table, and they write the shell's report buffer. They never touch chunk 6, so they need no trampoline of their own. The corpus through `RUN` runs with the banking invariant "no write to chunk 6 while the EXROM is paged in" armed.

**The texts** (`spec.md` §6.3). Some were shortened so that `ERROR n: ` and the text fit the 32-column row: `CONSTANT REQUIRED` (was "constant expression required"), `WRONG ARGUMENT COUNT` (was "wrong number of arguments"), and `MISPLACED BREAK`/`CONTINUE`/`CASE` (were "... outside loop/switch"). Two were made more exact: `BAD CHARACTER` (was "invalid character", to share the word) and `STRING TOO LONG` (was "token too long": only a string literal reaches it).

## 4. The reports

`RUN` shows `COMPILING` on the status row, compiles, and runs the program on a cleared screen. Every outcome then ends with a report on rows 22 and 23 in the status bar's colours: white on black, with V2's swatch on row 23.

| Outcome | Row 22 | Row 23 | Then |
|---|---|---|---|
| compile error | `ERROR 23: UNDECLARED IDENTIFIER` | `LINE 4` | the cursor on line 4, its text in the edit buffer |
| runtime error | `RUNTIME ERROR 4: BAD ARGUMENT` | `LINE 1` (nothing when unknown) | the cursor on the line where the failing function's definition starts |
| BREAK | `BREAK` | `LINE 1` | the same |
| the end | `EXIT 42` | `IMAGE 1610 B  HEAP 15302 B` | the editor as before `RUN` |

- **The report is drawn over the screen as it is.** After an error that is the editor; after a run it is the program's screen, and only rows 22-23 change (`report-over-program`). A key ends the report; the key is not typed into the editor. A key pressed before the report (during a compile, or BREAK) is discarded first. Phase 5 discarded only a key left by a run, so a key pressed during a long compile ended the error report at once.
- **The exit status** is shown signed (`EXIT -32768` … `EXIT 32767`; `unsigned main` returning 65535 shows `-1`), 0 for a void `main`, and `exit()`'s argument from any depth (`report-exit-status`).
- **The image's size** is the code and static data in the four image regions: each region's bytes less its free bytes between code and data (`IMG_LIM`). Region 4 reserved by `#pragma hires` (`[end][end]`) counts only data placed there before the pragma (`SH_IMAGE`, 51 B). It is checked against the declarations in `report-image-size`: the code below `CG_PC`, plus 2 + 10 + 6 B of globals, a 3-byte string and two 6-byte function → line records. It is also checked over the whole corpus against the harness's own computation from the limits, including programs that span regions (8,331 B, 12,702 B, 13,493 B with `#pragma hires`).
- **The free heap** is the largest block `malloc()` can return in that run: from the source's end (made even) to `LIB_HEAP_END`, less the block's 2-byte header (`SH_MEMORY`). `report-heap-real` reads it from a report, then runs the same program with `malloc(HEAP)` (non-NULL) and `malloc(HEAP + 1)` (NULL).
- **`FREE`** shows `SOURCE s B  FREE f B` / `IMAGE i B  HEAP h B`. These are the source's bytes in the line store, the room left up to the line store's ceiling (`VARS_START`), the last successful compile's image (0 before any), and the heap a run would have now. On an empty machine: `SOURCE 0 B  FREE 18432 B` / `IMAGE 0 B  HEAP 18428 B`. A key returns to the editor as it was (`cmd-free`).

## 5. Design decisions

1. **Two report rows.** One row of 29 columns cannot hold `ERROR n: MESSAGE` and the line number with useful messages, nor `EXIT n`, the image and the heap (up to 34 characters). Row 22 holds the headline and row 23 the line or the memory. Every message fits with its number (checked by the generator).
2. **The report is drawn over the screen as it is, until a key** (V2's and Phase 5's rule). The cursor goes to the error's line at once, so the editor shows that line when the key is pressed.
3. **The messages are generated from `include/leapc_errors.inc`**, so the ROM, the tests and `spec.md` cannot disagree.
4. **The diagnostics need no trampoline** (§3). The plan's "through a trampoline" assumed HOME code would format the messages; in the as-built design the EXROM shell formats them after the compile's own trampoline.
5. **`HEAP` is the largest `malloc()` block**, and `IMAGE` counts only code and data placed (not the regions' free gaps), so both match what a program sees.
6. **`COMPILING`**: a long program compiles for seconds (8-13 ms per line: about 7 s for Phase 4's 851-line capacity program), and Phase 5 showed nothing meanwhile.

### 7.2 The corpus through `RUN`

For each corpus program, `exectest.shell_run`:

1. Restores the booted editor, writes the source into the line store and enters the editor on the append line.
2. Types `r`, `u`, `n` and ENTER through the ISR's latch, so the shell's command matching runs.
3. Stops at `SH_COMPILE`, arms the banking invariants, and runs to the compile's end in `SH_RUN`. It reads the result and the compile's T-states.
4. For a program that compiled, stops at `RT_RUN`'s entry, then runs the program with the same loop as the direct path: keys fed, BREAK pressed, every `LEAVE` audited. The run ends at `RT_RUN`'s `ret`.
5. Snapshots the program's screen, system variables and chunk-6 RAM (paged out for the read and back in) and the AY registers. Then it runs to the report, reads it as built and as shown, presses a key and reads the editor.

Checks: the case's own expectations (exit value, compile error and line, runtime error and line, memory, golden code, regions, screen, AY, attributes, pixels, cells, BREAK state, stack low-water mark), the report (from the result: `gen_diag`'s texts, the image from the limits, the heap from the source's end), rows 22-23 showing it, the report waiting for a key, and then the editor at depth 1 with nothing running and the source unchanged. The cursor must be on the error's line with that line's text (the first 127 characters), or still on the append line.

Declaration cases (`tests/decl`, no `main`) must give their expected error, or `ERROR 71: NO MAIN FUNCTION`, with the same report and cursor checks.

Five lexical-error programs were added to `tests/experr` (11, 13, 14, 15 and 16 had only token-dump cases in `tests/lexer`, which `RUN` cannot run). They run in the direct path, the shell path and the canary.

### 9.1 Test execution time

| | Phase 5 | Phase 6 |
|---|---:|---:|
| `make test` (the runner, then the canary) | 2,511 s + 822 s = **3,333 s** (56 min) | **305 s**, including the canary and the 697 shell-path corpus cases that are new in Phase 6 |
| ZRCP command with a reply (`get-registers`, `read-memory`, `run`) | 41.0 ms | **0.04 ms** |
| A corpus case, direct path | 1.38 s | 0.02 s |
| A corpus case through `RUN` | — | 0.15 s (with the invariants armed: 0.18 s) |

There were two causes:

1. **ZRCP latency.** Every command with a reply took 41 ms. ZEsarUX writes a reply and its prompt separately; with Nagle's algorithm on its side and delayed ACKs on the client's, the prompt waited for the client's ACK. The harness's `ZRCP` client (a subclass of ts2068-debug's) sets `TCP_NODELAY` and re-arms `TCP_QUICKACK` around every `recv`. Phase 5 attributed the slow suites to breakpoint conditions; most of the time was this wait (the harness makes several commands per breakpoint stop).
2. **Parallel emulators.** `run_tests.py` runs every suite as tasks on one pool of 7 ZEsarUX instances (the CPUs less one, at most 8), the longest first. The tasks are 104: the corpus, the canary, `exec` and `decl` in shards, and each shell and workflow case on its own. Each worker reuses its emulator while the image stays the same. Measurements are emulated T-states, so the host's load does not change them (the measured values are as in Phase 5, §9.3).

Robustness:

- Workers are daemon processes that stop their emulator on SIGTERM, and the main process ends them on any exit.
- `Machine.start` refuses a port that already answers. Found when a crashed first attempt left workers and emulators on the same ports.
- `make canary` (standalone, 7 workers) remains.

### 9.2 Harness changes

- **`InExrom` breakpoints (`Machine.xsym`).** Chunk 6 is the EXROM or image region 1, so an EXROM label's address is also an address in a running program's code. A plain PC breakpoint on `SH_RUN.rtdone` fired inside programs. EXROM stops now carry the condition `PEEK(BANK_EXROM_DEPTH)<>0`, and the shell path's run ends on HOME's `RT_RUN.leave` (a label, no bytes).
- **`exectest.call_safe`.** It calls a probe routine with a stack 64 B below the live one and restores every register, so a stopped shell continues unharmed. `m.call`'s fixed stack at `$FF00` is just above the shell's frames.
- **`exectest.read_chunk6`.** It pages the EXROM out around a read of chunk-6 RAM (ZRCP reads what is mapped).
- **The Phase 5 RUN cases** expect the new report texts. `Shell._wait` returns a report as its two rows, and `Shell.press_code` presses any key, including ENTER, on the matrix.
- **`run_tests.py`** checks at the end that every compile error number was reported through `RUN` by a passing case.

## 11. Code audit

`make audit` (the z80-skills pattern scan), and every hint in the new code checked by hand:

- **`DG_APPEND`:**
  - Stack: `push bc`/`pop bc` around the number; one `push hl`/`pop hl` per word. The early `ret z` (no such key) comes after the `pop bc`.
  - `djnz .skipw` counts B = the word's number, 1-70, never 0: the generator numbers words from 1.
  - `inc hl` does not change flags, so `bit 7,(hl) / inc hl / jr z` tests the byte just passed.
  - The output is at most 32 characters plus NUL in the 33-byte buffer: the generator checks every report's length.
- **`SH_IMAGE`:** `push hl`/`pop hl` per region; IX walks `IMG_LIM` (the shell's routines already destroy IX). Region 4's special case is taken only when B = 1 and its free bytes are 0.
- **`SH_MEMORY`:** `push de`/`pop de` around the heap's computation; a source within 4 B of the top gives 0, not a negative heap.
- **`SH_FREE`:** `push hl` (`PROG_END`) / `pop bc`.
- **`SH_BAR_ROW`:** balanced `push`/`pop` of HL and AF; `djnz .bar` with B = 32 set just before. The texts fit the row.
- **`SH_RUN`:** `push de` before `SH_IMAGE`, `GFX_CLS` and `RT_RUN`, `pop de` after. `RT_RUN` always returns there: every end of the program unwinds inside it.
- **The report's key latch:** `SH_REPORT` clears `KBD_KEYHIT` before it waits.
