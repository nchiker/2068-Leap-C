## 4. The layout guard and the canary

### 4.1 Static census (`make check`)

`tools/check_ram_layout.py` reads both production listings and takes every name used by an emitted line of HOME (`$0000-$3FFF`) or EXROM (`$C000-$DFFF`) code or data, with the EQU closure (V2's `check_ram_layout.py` method). Every name whose value is a RAM address must be a system variable or Leap-C cell (208), a display-file-1 constant (3), one of the platform cells Leap-C keeps or a V2 alias of one (10: `GFX_LINE_X0..Y1` are V2's `EXTENSION_ARG0..3`), a region boundary or a value (30), or an EXROM label (57). It also checks the map (the eleven ranges tile `$4000-$FFFF`; the cells end below `$6000`; `PROG_AREA_START`, `PROG_AREA_MAX`, `LIB_HEAP_END`, `SECOND_DISPLAY_ADDR` agree with the map; the compiler's region table in the ROM, `IMG_TABLE`, equals the map) and that no Leap-C source uses a literal RAM address (three literals are values: `$8000`, the heap's in-use bit, and two `$FFFF` sentinels).

**Negative controls.** `--negative` assembles the HOME image eight times with `-DLEAPC_NEGCTL=n`, each referencing one misplaced cell from code appended after the production code, and requires each report: a cell in the source region (`$7810`), in image regions 2 (`$E100`), 4 (`$6100`), 1 (`$C100`) and 3 (`$F404`), in the stack (`$FA00`), at `$FF08`, and V2's `EXTENSION_MAGIC` (a platform cell Leap-C has no use for — the clear that delta D5 removed). All eight are reported; the production image's hash is unchanged by the control builds.

## 5. Image regions: every transition

Each instruction unit is placed only with 12 bytes free (`CG_GUARD`: the unit, a held operand's push, a linking `jp`); otherwise the code continues in the next region with room, linked by `jp`. Data goes to the first region with room for the whole object.

## 6. `#pragma hires`

`#pragma hires` makes image region 4 full from its line on: its limits become `[end][end]`, so neither the code nor the data allocator places anything there (`PP_HIRES`, 8 B). `mode(1)` (`LIB_MODE`) succeeds while region 4 holds nothing — untouched (`[base][end]`) or reserved (`[end][end]`) — and gives runtime error 3 otherwise. The directive dispatch was made reusable (`PP_DISPATCH`, no extra bytes), so `#pragma` looks its name up in its own record chain (`PP_PRAGMAS`); Phase 8's optional `#pragma size` would be one more record.

| Case | Shows |
|---|---|
| `hires_mode.c` | regions 1-3 full of data, the code in region 1's room; `mode(1)`, `plot`, `point` work; the mode back to normal at the end |
| `hires_toobig_code.c`, `hires_toobig_data.c` | regions 1-3 full: the code, or a global, is *program too big* (without the pragma they would go to region 4: `tests/lib/gfx/mode_refused.c`) |
| `hires_late.c` | data already in region 4 stays; `mode(1)` gives runtime error 3 at `main`'s line |
| `hires_late_code.c` | after a late pragma no new global goes to region 4 |
| `hires_twice.c`, `hires_macro.c` | the pragma twice and inside a function; a macro named `hires` does not affect it (directive tokens are not expanded) |
| `tests/pperr/pragma*.c` (6) | `#pragma once`, `lores`, `HIRES` (case), `#pragma` alone, `#pragma 1`: not supported; `#pragma hires please`: syntax error |

A late pragma cannot take back region 4: if the code already runs there it continues there (the code allocator reserves its units from the region's high end), and data already there stays. Both cases are caught at run time (error 3); `spec.md` §3.2 says to put the pragma first.

## 7. Stack and heap

### 7.1 The stack between two frame checks

`ENTER` checked the frame against a floor of `$F880` after moving SP. Phase 4 measured what can run *between* two frame checks, where nothing checks:

| Below the last frame check | Measured | Bound |
|---|---:|---|
| held expression operands | 2 B per level | the compiler's nesting guard: at most 62 levels, 124 B |
| pending call arguments (pushed right to left before the call) | 2 B per word | **unbounded before Phase 4** (see below); now 32 words, 64 B |
| a library routine below its arguments | up to 40 B (`puts`/`print` scrolling the screen through the platform's output; that measurement may include an interrupt) | 40 B |
| the IM 1 handler | 18 B | 18 B |
| the call and `ENTER`'s push of IX before the check | 4 B | 4 B |

**Two defects found by measurement.**

1. **Pending arguments had no bound.** Arguments are evaluated and pushed last first, so in `f(g(h(...), …), …)` the later arguments of every enclosing call stay on the stack while the first one is evaluated, and no callee's `ENTER` runs until the innermost call. The compiler's own stack bounds the nesting, not the arguments: 40 levels of 16-argument calls pushed 1,220 bytes before the first check; from a frame near the floor that writes through image region 3 into the platform cells (the editor's line buffer, the UDGs) and image region 2.
2. **A call with 256 arguments hung the compiler.** The argument count is 8 bits; at 256 it wrapped to 0, the 256 rewind marks stayed on the compiler's stack, and the compile never returned (578 million T-states, then stopped by the harness).

**Fixes.** `CX_CALL` counts the argument words pushed and not yet popped by the calls being compiled (`CX_PEND`) and refuses more than 32 with the current call's (*nesting too deep*; 17 B, ledger L27): a single call can pass 32 words (31 values to `printf`), and nesting counts what the enclosing calls have pushed. With every term bounded, the floor's margin is set to cover their sum: 124 + 64 + 40 + 18 + 4 = 250 B ≤ 256 B, so **`LEAPC_RT_STACK_FLOOR` = `$F900`** (asserted in `leapc_layout.inc`). `ENTER` now compares the new SP's high byte with the page-aligned floor *before* it moves SP (+1 B, L28), so a frame that does not fit is never made and an interrupt cannot push below it.

| Test | Result |
|---|---|
| `tests/mem/stack/floor_worst.c`: recursion to just above `$F900`, then 40 held operands around `itoa(printf(…30 values…), buf, 10)` (32 words pending) with `printf` scrolling | correct result and screen; **lowest stack byte `$F856`**, 86 B above `$F800` |
| `floor_big_frame.c`: recursion with 250-byte frames | stack overflow at the right line; nothing written below `$F9F0` |
| `args_256.c` (the former hang), `args_33.c`, `args_nested_33.c` | *nesting too deep* at the 33rd word |
| `args_32.c`, `args_nested.c`, `args_sequential.c` | 32 words pending (alone, and 15 + 17 nested) compile and run; sequential calls do not accumulate |
| `recursion_depth.c` | the reference function (one `int` parameter, one `int` local, 8 B a level) recurses **190 levels** from `main` before *stack overflow*: ($FEF2 − $F900) / 8 |

The cost is 16 levels of the reference function (206 with the old floor), 7.8%: the price of the guarantee that the stack never leaves its region.

### 7.2 The heap

The heap runs from the end of the source (made even) to the end mark at `$BFFE` (`spec.md` §3.2). `largest_block.c`: the largest block is the heap less its 2-byte header (18,316 B for a minimal program, §9); one byte more gives NULL; both ends of the block can be written; the end mark is intact afterwards and the block is reused after `free`. `many_blocks.c`: 16-byte blocks until NULL (962 of them), all inside `$7800-$BFFD`, adjacent and intact; after freeing all of them the whole heap is one block again. A compile that succeeds needs workspace for at least `main`, so the heap is never empty: at the largest source a minimal program compiles with, it is still 16 bytes (§9).

## 8. Banking invariants

`tools/memguard.py` arms three ZEsarUX breakpoint conditions (slots 9-11) for the compile and the run; ZEsarUX evaluates them after every instruction:

| Invariant (`spec.md`) | Condition |
|---|---|
| no stack in chunk 6 (§2.2 rule 2) | `SP>BFFFH and SP<E000H` |
| paging depth 0 while a program runs (§3.3), outside the trampolines' `NOBRK` sections | `PEEK(RUNNING)<>0 and PEEK(NOBRK)=0 and PEEK(BANK_EXROM_DEPTH)<>0` |
| nothing writes chunk 6 while the EXROM is paged in (§2.2 rule 3: the EXROM-resident constant folding and library-name search; the trampolines; the ISR) | `MWA>BFFFH and MWA<E000H and PEEK(BANK_EXROM_DEPTH)<>0` |

They are armed for every case of the canary sweep (§4.2): **none fired in 692 programs** (compiles that use constant folding and the library-name search through the EXROM, runs with `beep()`'s trampoline, BREAK in every state, the soak). Built-ins in `make test` (`phase4_builtins`):

**What the table says.**

- **Source is the binding limit for ordinary programs.** The typical program (76 modules of 11 lines; 17.7 B of line store per line) stops at *out of memory* with **15,087 B of source** (851 lines, 13,385 B of text) and **3,255 B of workspace** (about 43 B a module) in the shared 18,432 B region, while its image is 12,737 B of the 19,840 B available. The feasibility study (§5.2) estimated about 21.5 KB of source for the mixed templates, assuming that source and code share one 33 KB pool; the map gives the source and the workspace their own region and the image its own regions, so at the source limit about 7 KB of image stays unused. Its code is 0.73 bytes per byte of line store (0.83 per byte of text; the study's sample: 0.53), a dense sample of short lines with a loop and arithmetic in every function. The workspace per declaration is unchanged from M1.2: 13 B for a global scalar, a local or a struct member (4-character names), 20 B for a global array, 24 B for a two-parameter prototype.
- **The minimal program** leaves its source 20 B of workspace (`main`'s entry and its function type): 18,412 B of source. A source that compiles always leaves a heap (16 B at the very limit: the heap is the region above the source).
- **The image** takes 19,411 B of code and 266 B of data (function → line records, `g`) from code made by macro expansion: every region is filled to within 2 B, except region 4, where the next function (448 B) did not fit in the 158 B left. Static data alone reaches 19,817 B with a minimal `main`; one object is at most 8,192 B (region 1).
- **The stack** gives the reference function (one `int` parameter, one `int` local) 190 levels, 381 for a function with neither, 47 with four parameters and a 20-byte local array: (`$FEF2` − `$F900`) / frame.
- **The heap** gives a minimal program one 18,316 B block, and `tests/mem/heap/many_blocks.c` 962 blocks of 16 bytes (18 B with the header).
- **Nesting** is limited by the compiler's stack guard (`$F8C0`, *nesting too deep*) everywhere: held operands and nested calls at 60 levels are the lowest, all above the 32 guaranteed by `spec.md` §4.10. Struct nesting has no depth limit; 274 nested struct types fill the workspace.

## 12. Code audit

`make audit` (the z80-skills pattern scan) over `src/`; each hint in new or changed code was checked by hand:

- `RT_ENTER`: `cp LEAPC_RT_STACK_FLOOR >> 8` is a high-byte compare: the floor is page-aligned (asserted), and the new SP lies in `$F7xx-$FFxx` (SP is at most 250 B below the floor when `ENTER` runs, and n ≤ 255), so no wrap. SP moves only after the check; HL holds the function's address for `RT_ERR_STACK` as before. BC is no longer used.
- `LIB_MODE`: the `cp LEAPC_IMG4_END >> 8` compares the low limit's high byte when low = high; `LEAPC_IMG4_END` is page-aligned (asserted) and low ≤ high ≤ end in every reachable state of the region table (the code allocator's reserve, its chain-out at `CG_PC + 3`, `CC_FINISH`, the data allocator's test, the pragma's clip). The `DB $01` (`ld bc,nn`) skip keeps the flags of `or l`.
- `CX_CALL`: the count check runs in the counting pass, where `.skip` reloads A and does not use HL; the release after the call runs after `CX_POPY` and before `push bc`, and the code after reloads HL and A. Muted arguments (`sizeof`) count and release symmetrically. `CX_PEND` is a compiler cell, cleared at every compile.
- `PP_DISPATCH`/`PP_PRAGMA`/`PP_HIRES`: A is the token kind from `LEX_NEXT` on every entry; IX and NM are kept (a directive can come between any two tokens).
- D5/D6: `MEM_INIT` now destroys only HL (its header's AF, BC, DE remain allowed); no caller of `GFX_CLS`, `GFX_SCROLL_TEXT_UP` or `GFX_SET_MODE` used the registers `GFX_SPRITE_INVALIDATE` set (`GFX_SET_MODE` kept A around it).

## 13. Design decisions and deviations

1. **Baseline layout A is final**; the 340 unused bytes of V2 cells in `$F180-$F3FF` are recorded, not reclaimed (§3.1).
2. **The stack's floor is `$F900`** (was `$F880`), checked before SP moves: the recursion capacity drops 7.8% for a stack that provably stays in its region (§7.1).
3. **At most 32 argument words pending** (`spec.md` §4.10): new limit, *nesting too deep*. The spec's 16-parameter limit for declarations is unchanged; a call to a function without a prototype, or `printf`, can pass up to 32 words.
4. **`#pragma hires` clips region 4 from its line on**; a late pragma does not take back what is already there, and `mode(1)` then refuses (§6).
5. **Runtime errors in code continued from region 3 into region 4 have line 0** (`spec.md` §5.9): a fix costs about 9 B in `RT_ERRLOC` (0 B left) for programs above about 13.7 KB of image; the line is never wrong.
6. **Platform deltas D5 and D6** remove dead V2 stores (§11.3). Behaviour is identical: the cells have no reader.
7. **Harness changes** (purpose kept): the stack audit orders functions by allocation order (§5); the canary fills chunk 6 only while it is RAM (a ZRCP write goes to whatever is mapped: with the EXROM paged in it overwrote the emulator's EXROM image, found by `tests/rt/break_beep.c` under the canary).

## 14. Remaining risks

- **HOME has 524 B of reserve (12 B above its floor)** and 0 B left in expr, preproc, helpers, library, lexer, symtab, codegen and rtexit; decl and stmt have 1 B each. Committed allocations keep 141 B in the platform for Phase 5's glyphs and key map (estimated 80-90 B) and 340 B for Phase 7's tape block I/O. Phase 8's optional items (`#pragma size`, library additions, a peephole stage) have no HOME bytes: they need shrinking or an owner decision.
- **The stack's margin is derived from measured maxima.** The deepest library routine below its arguments measured 40 B (a scroll in `puts`/`print`, possibly with an interrupt inside), exactly the 40 B assumed in `leapc_layout.inc`'s `ASSERT` (which also adds the handler's 18 B separately). A later library routine (Phase 7's `tape_save`/`tape_load` trampolines, Phase 8 additions) must stay within 40 B, or the floor must move; `tests/mem/stack/floor_worst.c` and the canary's run low-water mark (`build/canary.json`) are the regression checks.
- **Source capacity is lower than the feasibility estimate** (15.1 KB for a typical program against about 21.5 KB): the source region, not the image, is the limit, and about 7 KB of image stays unused at that limit (§9). Real programs will show whether this matters; the layout is the spec's, and any rebalancing (for example giving display file 2 to the source region, which would drop hi-res support for large programs) is an owner decision, not proposed here.
- **Runtime-error lines are unknown (0) in code continued from image region 3 into region 4** (§5); only programs above about 13.7 KB of image can have such a function.
- **The recursion capacity dropped 7.8%** with the floor at `$F900` (190 levels of the reference function from the harness's call; the Phase 5 shell's own frames at `RUN` will take a few more bytes).
- **Contention.** Image region 4 (`$6000-$77FF`) lies in the ULA-contended RAM: code placed there will run slower on real hardware. Phase 9 measures it.
- **Testing is on ZEsarUX only** (Phase 9: Fuse, EightyOne, the TS2068). The banking invariants rely on ZEsarUX's breakpoint conditions; ZRCP writes act on whatever bank is mapped (a harness fact the canary now respects, §13).
