# Phase 9 — Emulator and physical hardware validation: milestone report

**Date:** 2026-10-21. **Status: complete, as far as emulation can establish it.** Every emulator criterion of `project_plan.md` §11 is met with measured evidence on the final production images (§1). **The physical TS2068 checks are not run.** No machine was available, and the owner accepted recording them as a qualification deviation, not as passes (2026-10-21). `docs/HARDWARE_CHECKLIST.md` and the kit (`make kit`) are ready for when a machine is available.

- **Two emulators.** The ROMs are qualified on ZEsarUX 13.0 (every suite) and, independently, on Fuse 1.9.1. Fuse runs headless through a small shim of its own entry points and is driven by the same expectations: the boot, every printable key on the keyboard matrix, 31 typed programs, BREAK, SAVE recorded on Fuse's tape deck, a WAV, and the corpus. All 746 of the corpus programs that need no key or BREAK during their run were LOADed from tape by the ROM's own loader and RUN, with no failures.
- **The 60 Hz finding.** ZEsarUX 13.0 runs its TS2068 with the 48K Spectrum's 50 Hz frame (69,888 T); Fuse uses the TS2068's own 60 Hz frame (58,688 T). Everything counted in frames (`frames()`, `pause`, `beep`, the keyboard's repeat, the start-up chime) is 20% faster on a real machine than on ZEsarUX. The timing comparison (§6) gives the same T-states on both for uncontended code (+0.6% on Fuse, from the extra interrupts), and +23% for code in the contended region 4 on Fuse against +15% on ZEsarUX.
- **Power-on RAM.** The boot from eight RAM patterns (four random seeds, `$FF`, `$55AA`, each address's low byte, and the reset button after a session) is byte- and T-state-identical to the boot from zeroed RAM. That holds after one fix: the UDG table was never cleared, so codes 144-164 drew power-on garbage. The corpus runs from every pattern, and the full suites from two (§4).
- **ROM coverage.** This is V2's method: ZEsarUX's code coverage over every suite, mapped onto the listings. **HOME executes 99.8% of its instructions and enters every routine; the EXROM executes 98.1%.** The gaps led to 23 new tests (21 corpus programs, 2 shell cases) and two removals of dead code (31 B). Every remaining unexecuted instruction is classified (§7).
- **Two defects found by Fuse.**
  - A key held past the keyboard's auto-repeat delay (35 frames, 0.58 s on a TS2068) ended a report or message on its own, so BREAK or RUN's ENTER held for about half a second made the report vanish before it could be read. Fixed in the shell (+5 B), with a regression test that fails on the Phase 8 ROM (§5.3).
  - Float code lost about 1% of the frame interrupts: V2's bank switch keeps interrupts off for about 120 T, longer than the TS2068's 32 T INT, and float code switches banks twice per operation. `frames()`, `pause` and the keyboard's timing ran slow in float-heavy programs. - **Owner-approved changes.** The digit `1` and the letter `l` are distinct in the font (platform delta D13, data only). An undeclared identifier's report names it: `LINE 3  'l'` (+39 B EXROM).

Every WAV decodes, through an independent decoder, to exactly its tape. The check programs load from their WAVs and run on both emulators.

## 3. Owner-approved changes

### 3.1 The digit `1` and the letter `l` (platform delta D13)

V2's glyphs differed in two pixels of the top rows: `1` was `$20,$60,$20,$20,$20,$20,$70` and `l` was `$60,$20,...,$70`. The owner had typed `l.0` for `1.0` and could not see why the compiler reported an undeclared identifier. The new `1` has a flag and a full-width base (`$20,$60,$A0,$20,$20,$20,$F8,$00`). The new `l` has a tail to the right and no base (`$60,$20,$20,$20,$20,$20,$18,$00`). Both stay distinct from `I`, `|` and `!`, in plain and in bold: bold is `byte | byte >> 1` and stays within the cell. The change is data only, with no size change. It was reviewed as a rendered image and checked by the shell's `glyphs-distinct` case, which requires every printable character's glyph to be distinct. The harness reads the screen with the ROM's own rendered glyphs, so no test needed changing. The delta is recorded in `platform/UPSTREAM.md`, and `make check` verifies it against the V2 tag.

### 3.2 The undeclared identifier's name

The report row `ERROR 23: UNDECLARED IDENTIFIER` already holds 31 of 32 columns, so the name goes on the status row after the line: `LINE 3  'l'`. Names longer than 15 characters show their first 15 and stay left of the colour swatch. The name is the compiler's `NM`: `CX_PRIMARY` looks the identifier up there, and nothing writes it between that lookup and the error (checked: `LEX_NEXT` and the macro hook do not). It points into the source in the line store, which the EXROM shell may read (bank rule 3), and an identifier from a macro's body points at the `#define` line. Cost: **39 B** of EXROM after a shrink pass. Tests: three typed programs on Fuse's and ZEsarUX's keyboard matrices (`undeclared-l`: the owner's own mistake, `undeclared-long`, `undeclared-macro`). Every error-23 case of the corpus through `RUN` is checked against the name in `NM`, which must be a whole word of the source (`tools/exectest.py`).

## 4. Power-on RAM

A real TS2068 powers on with whatever its DRAM holds, and its reset keeps the RAM; every earlier suite booted ZEsarUX from zeroed RAM. `tools/poweron.py` writes a pattern over `$4000-$FFFF` after `reset-cpu`, which keeps RAM and the registers a Z80 reset leaves alone (measured), and sets those registers too. The patterns:

- `random:1` to `random:4`: bytes and registers from Python's `random.Random(seed)`, reproducible;
- `ones` (all `$FF`);
- `alt` (`$55AA`);
- `addr`: each byte its address's low byte, so stale pointers read as plausible data;
- `warm`: the reset button after a session, with a program compiled and run first, its image and heap left in RAM.

**Checks.**

- The boot reaches the idle prompt in the same T-states and with the same SP as from zeroed RAM.
- Every byte the ROM defines there is the zeroed boot's: `$4000-$BFFF`, the UDG table, the edit buffer, and the live stack.
- The boot checks pass at that prompt.
- A slice of the corpus passes from that boot; the eight slices cover the corpus once, in `make test`.
- `run_tests.py --ram PATTERN` runs any suite from a pattern.

The areas left to vary by design are the image regions, the stack below SP, `$FF00-$FFFF`, the V2 cells Leap-C does not use, and `GFX_LINE_X0..Y1`. Programs and the compiler write all of these before reading them, and `draw()` sets all four `GFX_LINE` cells.

**Finding: the UDG table.** From every non-zero pattern, the only defined RAM that differed was `UDG_TABLE` (`$F180`, 168 B). The cold start never cleared it. Codes 144-164 therefore drew the RAM's power-on contents on a real machine, while ZEsarUX's zeroed RAM showed spaces, as the specification says characters without a glyph do. **Fix:** `COLD_CLEAR` clears the table and runs `MEM_COLD_INIT`; `COLD_START` calls it (+12 B, after the NMI vector, because the cold-start gap is full; ledger L56). With the fix, all 144 boot checks pass. The case `tests/lib/text/udg_blank.c` runs from every pattern. The RAM canary no longer fills the table, which is now defined RAM (`tools/memguard.py`).

**Results.** In `make test` (the final run): 8 patterns × 18 boot checks, **144/144**, and the corpus's 668 programs, one slice from each pattern, **668/668**. Every pattern's boot takes 4,626,111 T with SP `$FEFC`, as from zeroed RAM.

## 5. Fuse 1.9.1

### 5.1 The harness

Fuse has no remote-control protocol. `tools/fuse/fuseshim.c` is an `LD_PRELOAD` library for the Fuse binary. Fuse calls `SDL_PollEvent` once per emulated frame, from its frame event; the shim does its work there, between two frames in Fuse's own thread, and serves commands on a Unix socket. It drives only Fuse's own entry points:

- the keyboard matrix (`keyboard_press` and `keyboard_release`: the half-row bits port `$FE` returns);
- the debugger's command interpreter (breakpoints with commands, `print`);
- the tape deck (`tape_open`, recording, `tape_write`);
- the memory map, for reading.

Their addresses come from `nm` of the unstripped binary, and the structure sizes the shim mirrors are checked against the symbol table. Fuse runs headless (SDL's dummy video driver, no sound) at `--speed 20000`: about 7,700 frames a second, 130 times a real machine, where it saturates a host core. Typing is paced by the machine, as in the ZEsarUX harness. A chord is pressed only while the PC is in `IO_READ_KEY`'s loop (or, at a frame's interrupt, the PC it interrupted). It is held until a debugger breakpoint's counter shows `IO_LATCH_AND_CLEAR` has run, then released. The screen is decoded with the ROM's own glyphs. Tape traps are off, so the ROM's loader reads Fuse's EAR signal.

Found on the way: Fuse's `--debugger-command` refuses a newline after the last command. A breakpoint on `IO_READ_KEY` fires on every pass of its loop, which slowed Fuse to one frame a second, so the handshake reads the PC instead. Fuse's error dialogs re-enter `SDL_PollEvent` (the shim answers them with Return). This Fuse's libspectrum has no WAV reader, so the harness plays a WAV's samples as a TZX direct recording.

### 5.3 The defect: a report ended by a held key

Fuse's BREAK case first showed a `BREAK` report vanish while CAPS SHIFT + SPACE was still held. The ISR auto-repeats a held key after `KBD_REPDEL` = 35 frames. `SH_REPORT` cleared the latch once, before drawing, and then waited, so the repeat of the key that caused the report ended it. The same happened to RUN's ENTER held over a short program, and to any status-row message after a command. ZEsarUX's suites never held a key that long: they read the report at `SH_REPORT`'s entry. **Fix:** `SH_WAIT_KEY`, the shell's "press a key" wait, first waits until the ISR tracks no key (`KBD_CUR_ROW` = `$FF`). It then drops any key latched before or meanwhile, and waits for a new one (+9 B, replacing `SH_REPORT`'s clear, −4 B; ledger L58). **Tests:**

- the shell case `report-held-key` holds BREAK on a running loop, and RUN's ENTER over a short program, for 100 frames after the report appears: the report must stay up, and wait for a key after the release. On the Phase 8 shell it fails both ways; with the fix it passes;
- Fuse's BREAK case holds BREAK for 2 s at 60 Hz.

The harness's own key holds now release at the report, as a person would (`Shell._wait(on_message=...)`).

### 5.4 The defect: frame interrupts lost in float code

The 30-minute soak (H10, §8) on Fuse counted 107,807 frames where Fuse ran about 108,000. A probe compared Fuse's own frame count with `FRAMES` over 20,000 frames of three running programs: an idle loop and an integer loop lost none, and a float loop lost 209 (1.0%).

**Cause.** Every float operation calls the EXROM's float core through a trampoline that pages chunk 6 in and out (`BANK_PAGE_EXROM_IN` and `_OUT`, V2's `kernel/bank/bank.asm`). Both routines start with `di` and end with `ei`, so interrupts are off for about 120 T at a time. The TS2068's INT lasts 32 T (Fuse's TS2068 timings, from libspectrum). An interrupt that arrives inside the window is never taken, so the ISR misses that frame: `FRAMES` does not count it and the keyboard is not scanned. ZEsarUX's suites could not see this, because they read `FRAMES` itself rather than an independent frame count.

**Fix (platform delta D14, ledger L60, −2 B).** Both `di` instructions are removed. The `ei` instructions stay, so interrupts are on when the routines return, as before. The `di` protected nothing:

- The ISR (`KBD_ISR_TICK`) touches only `FRAMES`, the keyboard cells and the BREAK request. It never touches the paging depth, `PORT_FF_SHADOW`, the paging ports or chunk-6 RAM, and the stack is above chunk 6.
- A BREAK unwinds a program only with `NOBRK` at 0, and every runtime page-in is inside a `NOBRK` trampoline. After any unwind, `RT_RUN` restores the depth and the paging.

**Test.** The Fuse case `frames` runs an integer loop and a float loop for 6,000 frames each, and requires `FRAMES` to count every frame. On the earlier images (`ac821de5…`) it fails (5,966 of 6,024); with D14 it passes. The probe's float loop then counts 20,053 of 20,053 frames.

## 7. ROM coverage

### 7.1 Method

During the phase the owner noted that V2 tested every ROM function. V2's tool for that was ZEsarUX's code coverage (`tools/qual/qdiff.py`, `qcov_changed.py`). Leap-C now does the same on every `make test`:

- **Collection.** `run_tests.py --coverage` re-enables ZEsarUX's `cpu-code-coverage` after every snapshot load (a load switches it off). It harvests the executed addresses at every restore and at the end of each task, per image. The test image's runs count where it is byte-identical to production: HOME up to `LEAPC_HOME_CODE_END`, and the whole EXROM, as `make check` proves.
- **Chunk 6.** It is the EXROM or a program's image region 1, at the same addresses. While a program has run, chunk-6 addresses below its region-1 code end are dropped, so the EXROM's figures are conservative.
- **Report.** `tools/romcov.py` maps the addresses onto the listings' instructions (data and macros excluded) and reports per routine (code labels from the listing) and per file (`build/romcov.md`).

## 12. Code audit

`make audit`'s pattern scan and a manual audit of the phase's ROM changes:

- **`COLD_CLEAR`:** reached with SP set and interrupts still off from the reset. It fills 168 B (`UDG_COUNT * 8`; `sysvars.inc` asserts `UDG_TABLE + 168 = EDIT_LINE_BUF`) and tail-calls `MEM_COLD_INIT`, so the stack is balanced.
- **The name's report:**
  - It runs only for error 23, which `CX_PRIMARY` alone raises with `NM` set. A run or BREAK reaches it with `CC_ERRNUM` 0, and an unknown line skips it.
  - It copies 1-15 bytes from the source region (`$7800-$BFFF`), never chunk 6 (bank rule 3).
  - The status buffer's worst case is 30 characters and the NUL, against its 33 B, and the text stays left of the swatch (columns 0-28).
  - The NUL comes from B, which is 0 after `ldir`.
- **`SH_WAIT_KEY`:** it changes only A before its call. All its callers run with interrupts on (the ISR keeps `KBD_CUR_ROW`). There is no race with a new key: a key first seen during the release check needs two more interrupts before it can latch.
- **Delta D14 (`BANK_PAGE_EXROM_IN`/`_OUT` without `di`):**
  - An interrupt can now come between the depth update and the port writes. The ISR reads and writes none of that state, and runs from HOME with its stack and cells above chunk 6, so either paging state is safe for it.
  - Every caller gets the same exit state as before: interrupts on, from the routine's own `ei`. A caller that entered with interrupts off keeps them off until that `ei`, as before.
  - `COLD_START` (interrupts off from the reset) and the tape trampoline (interrupts off during a block) enter the routines with interrupts already off, so nothing changes for them.
- **`LIB_PARAMS`:** moved to mid-page, because the shell's growth had pushed it across a page boundary. Its `ASSERT` caught that at assembly.
- **The pattern scan's hints** in this code are false positives: a cell store, and `RT_ERROR`'s unwind (Phase 3).

## 13. Limitations and remaining risks

- **Physical hardware** (§10): every item is open until a machine is available.
- **ZEsarUX's 50 Hz TS2068.** The qualification emulator's frame is not the machine's. Results in frames from ZEsarUX are 20% slow; use Fuse's figures for a TS2068.
- **The EXROM coverage figure is conservative** (§7.1). A few entry points that only running programs call (`beep()`'s EXROM jump) count as unexecuted, although the library's tests run them.
- **Fuse's harness** depends on the unstripped Fuse 1.9.1 build on this machine (`~/fuse-build`), on gcc and on SDL2. Its symbol and structure checks fail loudly on another build.
- **Reserves:** HOME 76 B above its floor, EXROM 55 B.
