## 2. Owner decisions

### 2.1 The frame's reference point (`spec.md` §5.2, §5.3; v0.2)

**Finding.** `spec.md` v0.1 put IX at the lowest local (`IX+0 … IX+N-1` locals, arguments from `IX+N+4`) and required inline `(ix+d)` access for locals *and parameters* (§5.5). Two facts made that unworkable:

- The frame size N is known only at the end of the function body, after the parameters have been used.
- The Z80's `(ix+d)` displacement is **signed** (−128…+127), not unsigned as §5.2 assumed. Once `N+4+2k > 126`, a parameter cannot be reached inline at all, and §4.10 allows 255-byte frames.

**Decision (owner, 2026-10-13).** IX points at the saved IX: locals at `IX-1 … IX-N`, the return address at `IX+2`, arguments from `IX+4`. The stack's memory layout and the caller's convention (arguments pushed right to left, first lowest, popped by the caller, result in HL, IX/IY preserved) are unchanged. `ENTER n` = push IX; IX = SP; SP −= n; stack check. `LEAVE` has no operand (SP = IX; pop IX; return) and fits its RST slot.

**Effect.** Argument offsets (`IX+4+2k`) and local offsets (`IX-(offset+size)`) are known when used: no fixups. `return` anywhere is 1 byte. Locals within 128 bytes of IX are reached inline; frames up to 255 bytes use an address template beyond that (`push ix / pop hl / ld bc,d / add hl,bc`, tested in `tests/expr/frame/big_frame.c` and `tests/golden/frame_far.c`).

### 2.2 Budget (ledger L8, provisional)

After the shrink pass, the EXROM move (L5) and every reallocation that kept both reserves at or above their floors (L4, the HOME reserve down to 512 B), M1.3 was 269 B short. The owner chose a **provisional transfer of 269 B from the statements component** (Phase 2): a temporary allocation, not a demonstrated saving. The 512 B HOME floor, the code-generation optimisations and the optional FP calculator are kept. Phase 2 measures the statement compiler; if it needs the bytes, the protocol applies and any reserve-floor decision returns to the owner (§3.2).

### 4.1 How code is generated

- **Single pass, no IR.** The parser calls the code generator as it recognises each operation; code goes straight into the image.
- **Operand descriptors.** An operand is *deferred* (no code yet: a constant, an address constant, an object at a constant address, an object in the frame at `IX+d`, a function) or *resident* (its code is emitted: an address or a value in HL, or a condition in the flags). A deferred object keeps its own type until it is loaded, so the load has the object's width.
- **Held operands.** While the right operand of an operator is parsed, a resident left operand stays in HL. If the right operand needs code, the first instruction emitted pushes HL (`CG_UNIT`), and the operator pops it into DE; if it needs none, `ex de,hl` replaces the push and pop. A held operand is always the newest resident one, so the run-time stack follows the parse.
- **Conditions.** Comparisons and `!` leave a condition in the flags (`OK_COND`); a condition is turned into 0/1 only when a value is needed, and jumps test it directly.
- **Instruction units and regions.** Every instruction (or unit of up to 8 bytes) starts with `CG_UNIT`, which keeps `CG_GUARD` bytes above the code reserved against static data allocated meanwhile, and continues the code in the next region with room through a `jp` when the current one is full (spec.md §3.2; tested in `tests/run/region_*.c`).
- **Fixup chains.** A forward jump or a reference to a function not yet defined is emitted with the previous reference's address as its operand; defining the label or the function walks the chain. A function's chain ends with the line of its first use, which `E_UNDEFFN` reports. Chains run through code (`call f`, `ld hl,f`) and through static data (`int (*t[])(void) = { f, g };`).
- **Droppable tails.** Code that only computes the value of an expression after its side effect (the old value of `x++`, the extension of a byte just stored) is dropped when the value is not used: `i++;` is `inc hl` and a store, as in the spike.
- **Muted code.** `sizeof` operands and the operand a constant `?:`, `&&` or `||` does not evaluate are parsed and typed but emit nothing.

**Against the spike's 92 B core** (`LDL` 17, `STL` 17, `ENTER` 18, `LEAVE` 16, `LDI` 5, `STI` 6, `CMPLT` 13): Leap-C's equivalent core is **60 B** (`ENTER` 31 with its stack check, `LEAVE` 5, `LDI` 5, `STI` 6, `CMPLT` 13), 30 B of it in the RST slots. `LDL`/`STL` belong to the optional size template set (spec.md §5.6) and are not built. The whole helper core is 137 B: 30 B in page zero and 107 B in `src/runtime/helpers.asm`.

**Against the spike's times:** `LDI` 45 T and `STI` 49 T at the vector meet the plan's target exactly (the spike's RST-through-`jp` versions: 55 and 59 T). `CMPLT` 47-62 T (spike: 80 T by CALL, 217 T through the dispatcher). An empty function with 2 B of locals costs 231 T including the stack check (spike: 282 T with RST helpers, 125 T all inline). Inline frame access 38 T as in the spike.

**Slow spots:** division (≈ 3.6 kT) and multiplication (≈ 1.4 kT) are the kept V2 routines; `MATH_UDIV16` keeps its state in memory cells. A register-only divide would be about twice as fast for more ROM; a Phase 8 candidate if programs need it. Pointer scaling by 2-16 and constant multiplication by powers of 2 avoid `MUL` (`add hl,hl`).


## 7. Compile speed

**Method.** The T-states of `CC_PROGRAM` for every executable case that compiles, interrupts on (as a real compile), divided by the case's source lines (comments included).

| Corpus | Cases | Lines | T/line | ms/line (3.528 MHz) |
|---|---:|---:|---:|---:|
| Generated operator cases (dense: every line an expression) | 120 | 5,920 | 54,263 | **15.4** |
| Hand-written expression cases | 48 | 879 | 37,209 | 10.6 |
| Golden cases | 47 | 245 | 16,283 | 4.6 |
| Runtime cases | 10 | 144 | 26,158 | 7.4 |
| **All** | **225** | **7,188** | **50,320** | **14.3** |

All are below the 25 ms per line target (`spec.md` §6.3); for comparison, V2's compiler measures about 18 ms per line, and M1.2's declaration-only corpus 4.0 ms. The generated cases are the worst case: each line is a full expression statement with calls and conversions. The constant-folding trampoline adds about 240 T per folded operation; folding is rare in code (operations on two constants).

**Run time (for orientation; Phase 2 compares the spike workloads formally).** `fact(7)` 13,826 T including the program start (the spike's mixed `fact(7)`: 13,874 T, written with `if`/`return`); `fib(15)` 940,463 T (267 ms); `ack(2,3)` 22,135 T; `sum(180)` with a local per level 91,284 T.

| **Fixed cells** | +30 B (code generator state, call state, `RUN_MAIN`, the dummy region); the Leap-C cells use 263 B of the 678 B area (`$5D5A-$5E60`), 415 B left |

## 9. Design decisions and deviations (recorded, not silent)

1. **Frame reference point** (owner decision, §2.1; `spec.md` v0.2).
2. **Arguments are evaluated right to left** (the last argument first), the order in which they are pushed. C89 leaves the order unspecified. The first pass over the argument list only marks where each argument starts (it is lexed again when evaluated).
3. **A call to an undeclared function declares it** as `int f()` at file scope (C89 6.3.2.2). An undeclared name not followed by `(` is `E_UNDECL` at its own line.
4. **Undefined functions** that are used (called, or their address taken outside `sizeof`) are `E_UNDEFFN` at the line of the first use, at the end of the compile. A program without `main` compiles (`CC_COMPILE`) but cannot be run: `CC_PROGRAM` reports `E_NOMAIN` at the last line. `void main` exits with status 0.
5. **An `extern` object of incomplete type has no storage until its defining declaration** (M1.2, decision 5); using it in an expression before then is `E_INCOMPLETE`. C89 would allow `extern int a[]; ... a[1] ... int a[4];` (single translation unit; very rare).
6. **Struct assignment** (`s1 = s2`) is `E_NOTSUP` (`spec.md` §4.4 lists simple assignment; struct parameters and return values are already "not supported"; copy members or use pointers). A struct argument to an unprototyped function is `E_OPERAND`.
7. **`void` operands of `?:`** are accepted (`c ? f() : g()`); struct operands are `E_OPERAND`.
8. **`const`** is enforced for assignment, `op=` and `++`/`--` of an object declared `const`, its array elements and its struct members (`E_CONST`, new). Pointer targets are not tracked (M1.2 decision 8).
9. **Shift counts** above 15 shift every bit out, at run time as in constant folding (C89: undefined). `>>` of a signed value is arithmetic (spec.md §4.4).
10. **A constant condition of `?:`, `&&`, `||` selects at compile time**; the operand it does not evaluate emits no code. With a run-time condition the value of `&&`/`||` is materialised (`ld hl,1 / jr / ld hl,0`); Phase 2's `if`/`while` may test conditions directly.
11. **Code-size choices measured against the spike's mixed templates:** `inc hl`/`dec hl` for constants ±1..3 and `ld bc,k / add hl,bc` beyond (DE stays free); `add hl,hl` for ×2..16; the left operand of an operator kept in HL (`ex de,hl`) when the right one needs no code; the old value of `x++` and byte extensions dropped when unused; the final `rst LEAVE` dropped after a `return`. Constants are not moved to the right of commutative operators (`1 + x` loads 1 into DE).
12. **Pointer differences** divide by the element size with `RT_DIVS` (sizes other than 1).
13. **Program start (minimal, spec.md §5.7).** `RT_RUN` runs `main` on the caller's stack (the shell's SP; Phase 3 adds `SP = $FF00` with the shell's exit path), records `RUN_SP`, pages the EXROM out whatever the depth and restores the depth and paging afterwards, also after a runtime error. Static data needs no start code: the compiler writes it into the image (M1.2 decision 7).
14. **The EXROM entry table** gains `LEAPC_EXROM_FOLD` at `$C003`; constant folding runs in the EXROM (§3.2).
15. **M1.2 test changed:** `tests/decl/err/constexpr_function_address.c` expected `E_CONSTEXPR` for `int (*fp)(void) = f;`, the interim behaviour of M1.2. Function addresses in initialisers are supported now; with `f` never defined the same source gives `E_UNDEFFN` at line 3, and the case is renamed `undefined_function_address.c`. The positive cases are in `tests/expr/fnptr/`.


## 10. Code audit

**Pattern scan.** `make audit` (z80-skills `audit-z80` pattern scan over `src/`); every hint in the new files was checked by hand:

| Hint | Finding |
|---|---|
| `djnz` loops with calls (`CG_SEQ0`, `CG_MULK`) | `CG_B` keeps B |
| Conditional `call`/`jp`/`ret` after other instructions | each follows a flag-neutral `ld` after the flag-setting instruction (`CG_STORE`, `CG_CMP`, the helper dispatch, `FUNC_DEF`'s final LEAVE) |
| `ex (sp),hl`, `ld sp,…`, `add hl,sp` | the deliberate protocols: `CX_COND`'s chain swap, `RST LEAVE`, `RT_ENTER`, `RT_ERROR`'s unwind |
| `jp (hl)` | `CX_PUSHX`/`POPY`, the prefix-operator dispatch, `RT_ENTER`'s continuation, `RT_CALLHL` |
| `push ix`/`pop ix` | balanced on every path, including `RT_RUN` after a runtime error |
| `ldir` (string literals) | BC ≥ 1 (length + 1) |

**Run-time audit.** Every executable test stops at each `rst LEAVE` (up to 64 per run) and checks that SP is exactly at the function's frame (no temporary left, every argument popped by its caller), and after `main` returns that IX is the caller's again and SP is where the run started.

**Bugs found during M1.3 and fixed** (all by the corpus): `CX_BINARY` re-read its saved precedence from under the held operand (right-associative parsing of `a - b - c`); `CX_CALL` saved registers around `LEX_MARK`, which pushes under its return address; a clobbered displacement after `CG_NEAR`; a carry flag lost before a byte store; an argument list without `)` reported at the next line.


## 11. Remaining risks

- **HOME reserve at its floor (512 B), with 269 B of Phase 2's statement budget lent to M1.3 (L8).** Phase 2 must measure the statement compiler first (`if`/`while`/`do`/`for`/`switch`/`goto`/labels, local initialisers, the line table: estimated 650-700 B against the 685 B left). If it needs the bytes, the protocol applies and any reserve-floor decision goes to the owner.
- **The EXROM reserve is 334 B (floor 256 B).** Further cold-code moves (the type checks, the preprocessor) need either EXROM space or the Phase 8 decision on the optional FP calculator (2,165 B).
- **Expressions and code generator have no spare bytes.** Phase 2 changes there (e.g. testing `&&`/`||` conditions directly in `if`) must be paid by shrinking.
- **Compile speed** is measured on expression-dense test programs; Phase 6 measures the full corpus through the shell.
- **Only ZEsarUX is exercised** (Phase 9: Fuse, EightyOne, hardware).
