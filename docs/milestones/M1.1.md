### 4.2 Lexer: 102 cases, 102 pass

Each case is written into the real line store and lexed by the ROM through `TEST_LEX_DUMP`, with chunk 6 paged out as for a compile. Two independent checks apply to every case:

1. **The ROM's token dump equals the host reference lexer `tools/clex.py`** on every field: kind, line-start flag, unsigned and character-constant flags, line, value or bytes, and the error with its line. `clex.py` was written independently from `spec.md` §4.1; it reads the token and error numbers from the include files.
2. **The case's hand-written `// expect:` list** (tokens, values, lines, line-start flags) or `// expect: error E_x line` matches.

During development, check 2 caught five mistakes in hand-written expectations. Check 1 never disagreed with the ROM. Both checks are therefore live, and they are independent of each other.

## 5. Lexer throughput (measured)

**Method:** `TEST_LEX_COUNT` runs on the test image, timed from `.t0` to `.t1` with ZEsarUX's T-state counter. Interrupts are on, as during a compile, so the figures include the IM 1 handler.

**Sample:** `tests/bench/lex_sample.c`, a realistic 89-line program: a snake game with structs, arrays, a switch and library calls. Its token stream is first checked against the reference lexer.

| Sample | Lines | Text bytes | Tokens | T-states | T/byte | T/token | T/line |
|---|---:|---:|---:|---:|---:|---:|---:|
| `lex_sample.c` | 89 | 2,114 | 592 | 845,763 | **400** | 1,429 | 9,503 (**2.69 ms**) |

**By token class** (synthetic 1.5-2.2 KB inputs, the same method):

| Class | T/byte | T/token |
|---|---:|---:|
| Blanks (indentation) | 58 | — |
| Comments | 59 | — |
| String literals | 208 | 4,098 |
| Identifiers | 346 | 1,812 |
| Punctuators | 463 | 1,111 |
| Keywords | 501 | 2,857 |
| Hex constants | 551 | 3,349 |
| Decimal constants | 649 | 2,588 |

**Against the compile-speed target.** `spec.md` §6.3 sets ≤ 25 ms per line. Lexing realistic source costs 2.69 ms per line, about 11% of the target; for comparison, V2's whole compiler runs at about 18 ms per line.

**Speed changes made in M1.1:**

- A lowercase fast path in the identifier loop, and counting down instead of comparing for the 31-character limit: 438 → 400 T/byte for +7 B.

**Candidates if Phase 6 measurements need more:**

- A 96-entry character-class table, which would replace the `cpir` punctuator search and the `LEX_DIGIT` calls: about +70 B.
- Multiply-by-shift in `LEX_ACCUM` for base 10.

The lexer has 13 B of budget left. Either candidate would need bytes from another component under the `project_plan.md` §1.2 protocol.

## 8. Code audit

**Pattern scan.** `make audit` runs the z80-skills `audit-z80` pattern scan over `src/` (output in `build/audit_pattern_scan.txt`). Each hint was checked by hand:

| Hint | Finding |
|---|---|
| `cpir` | BC = 25 is never 0; Z = found |
| DJNZ loops with calls | `LEX_DIGIT` and `.next` preserve B and C |
| Non-local `pop hl` and stack deltas | Every push and pop is balanced on normal paths. The `.ovf` exit pops all 3 pushes |
| SP loads in `CC_ERROR` / `RT_ERROR` | Intentional unwinds to the recorded entry SP |
| Stale-flag branches | Each is the `or a; sbc hl,de; add hl,de` compare idiom, which keeps C and Z, or a branch after a flag-neutral `ld` |
| `di; halt` in page zero | The intentional `RST_UNASSIGNED` trap |

**Change made by the audit.** End-of-source detection in `LEX_SEEK` changed from `HL == PROG_END` to `HL >= PROG_END`, so a damaged store cannot run the lexer past its end (0 B).

**Register contracts.** Every new routine states In / Out / Destroys. The callers were checked against them: `LEX_CHAR` destroys BC and DE, and neither string loop keeps anything there; `LEX_ACCUM` keeps C, the base, which the number path relies on.

**Not a gate.** The `audit-z80` skill is a review method, not a pass/fail tool, so `make audit` is not part of `make check`.

## 9. Implementation decisions and deviations (recorded, not silent)

1. **Source streaming reads the line store in place, with no 264-byte copy window.**
   - The plan said "after V2's 264-byte window design". V2 copied records into a window. In the Leap-C layout the source region is always visible to the HOME compiler, so the lexer walks the records directly: at each CR, `LEX_NEWLINE` steps over the next record's length word, or onto a ROM `$00` at `PROG_END`.
   - This saves the window's 264 B of fixed RAM (the cells now use 157 B of the 678) and the refill code, and removes the per-byte copy.
   - Re-scanning from a saved point is trivial: save `LEX_PTR`, `LEX_LINE` and `LEX_BOLP`. M1.2 and M1.3 can use that for one-token lookahead.
   - The spec's mention of a "264-B source chunk window" in the fixed-cell area should be read as unused.
2. **Decimal constants 32768-65535 have type `unsigned int`.** C89 would make them `long`, which Leap-C does not have. Hex and octal follow C89 exactly (int, then unsigned int). This is a clarification of `spec.md` §4.1 "typed per C89 rules for a 16-bit int".
3. **Adjacent string literals are separate `TK_STR` tokens; the parser concatenates them** (M1.3) in the compile workspace, the string-literal staging of `spec.md` §3.2. The lexer's buffer therefore holds one literal at a time, with at most 125 bytes from a 127-character line.
4. **`\?` is accepted.** C89 has it; the `spec.md` §4.1 list omits it.
5. **Lexer features added now for Phase 2's preprocessor:**
   - `TF_BOL`, the first token on its line. Comments do not clear it, so `/* c */ #define` is a directive, as in C.
   - `LM_EOL` mode, which returns end-of-line tokens. A comment that spans lines inside a directive continues the directive, as in C.

   Both are tested.
6. **Compile error exit.** `CC_ERROR` (15 B) is counted inside the lexer component, since no "compiler common" budget exists. Error numbers are grouped by tens, by group (`include/leapc_errors.inc`). The message texts belong to the Phase 6 diagnostics.
7. **RST `$08-$30` vectors stop the machine** (`RST_UNASSIGNED`: `di; halt`) until the M1.3 helper core fills them. No M1.1 code uses them.
8. **Code assembled but not yet reachable:**
   - the editor engine, until the Phase 5 shell;
   - the FP calculator, which has no HOME entry until the Phase 8 decision. Its exit trampoline name maps to `BANK_PAGE_EXROM_OUT`, exactly as in V2.

   Both are inside their budgets and measured.
9. **V2 platform cells.** `MEM_INIT` still clears the V2 package and sprite cells, which lie in the `$F180-$F3FF` platform-cell area of the spec's map. This is harmless; trimming it is Phase 4 layout work.
10. **Platform finding.** `STORAGE_SAVE`/`STORAGE_LOAD` (EXROM) take and destroy IX, and the editor engine uses IX. The HOME platform uses neither IX nor IY, which confirms `spec.md` §5.1 for everything compiled code calls. The Phase 7 `tape_save`/`tape_load` trampolines must preserve IX. This is recorded in `platform/UPSTREAM.md`.
11. **`c2src.py` rules.** It expands tabs to 8-column stops and refuses lines over 127 characters and bytes outside ASCII 32-126, as the editor does.

## 10. Remaining issues and risks

- **Lexer headroom is 13 B.** Phase 2 macro expansion must be paid from the preprocessor budget (300 B). Its lexer hooks are small, because `LEX_PTR` can be redirected to a macro body.
- **EXROM retained platform has 3 B left, and the FP component 0 B.** Any platform delta in EXROM goes through the ledger.
- **Only ZEsarUX is exercised.** Fuse and EightyOne are courtesy emulators (Phase 9).
- **Owner-side items, none blocking M1.2:**
  - Physical key legends for the C punctuation must be verified before Phase 5.
  - No GitHub remote yet.
- **The `audit-z80` skill is user-invoked.** M1.1 used its pattern scan plus a manual review. The full skill review (`/audit-z80 diff`) can be run by the owner on this commit.
